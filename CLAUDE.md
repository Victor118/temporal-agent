# CLAUDE.md

## Build & Run

- Go n'est pas installé localement. Toujours utiliser Docker :
  - `cd /home/victor/dev/temporal-agent && docker compose up -d`
  - `docker compose exec agent go build ./...`
  - `docker compose exec agent go test ./...`
  - Tests du store sur une base jetable, jamais `agent` : `docker compose exec -T postgres createdb -U agent agent_dev_tmp`, puis `docker compose exec -T -e TEST_DATABASE_URL='postgres://agent:agent@postgres:5432/agent_dev_tmp?sslmode=disable' agent go test ./store/`, puis `dropdb -U agent agent_dev_tmp` de la même façon
  - Contre le vrai serveur Temporal (fin d'un participant sans perte de signal, `UNHANDLED_COMMAND`, continue-as-new ; sauté sans `TEMPORAL_SMOKE_HOST`) : `docker compose exec -T -e TEMPORAL_SMOKE_HOST=temporal:7233 agent go test -count=1 -timeout 20m -run RealServer -v ./workflow/`. Environ 4 min ; queue `smoke-signals-<rand>` à lui, tour et activities simulés, aucune base ; `TEMPORAL_SMOKE_MESSAGES` (200 par défaut). À relancer après tout changement de la boucle du participant ou une montée de version du SDK ou du serveur
  - Lancement réel du binaire : `agent/scripts/smoke.sh` (depuis l'hôte, compose démarré) : `agent dev` construit dans `/tmp/smoke-<rand>` du conteneur, queue `smoke-<rand>`, base `agent_smoke_<rand>`, clé LLM invalide exprès (un vrai appel à Anthropic, refusé en 401 : il faut le réseau), sans `RUN_AS_UID` ; deux messages, état, historique (deux `turn_error`), arrêt, suppression. Base supprimée et dossier effacé à la sortie, échec compris
- Pas de hot-reload : le `CMD` du Dockerfile compile une fois au démarrage → `docker compose restart agent` après une modification
- Port 8888 exposé pour l'API HTTP

## Architecture

- 3 modes : `agent server`, `agent worker`, `agent dev` (les deux combinés). `worker` et `dev` construisent leurs workers par le même `newWorkerRuntime` (`cmd/agent/runtime.go`) : mêmes workflows, activities et outils ; seuls diffèrent la destination des notifications web et la source des skills. Les outils Claude Code ne sont enregistrés que là où la CLI `claude` est installée. Fournisseur LLM choisi par `provider.New(LLM_PROVIDER)` (registre, `provider.Register`)
- Server = API HTTP + SSE hub + catalogue agents + skills versioning
- Back-office `/admin` (htmx + `html/template`, `web/admin`) : agents et utilisateurs, réservé au rôle `admin`. Le JSON du panneau admin du chat est sous `/api/admin` (admin aussi)
- Règles des sessions dans `session.Service` (`session/`) : ouvrir, livrer un message, forker, inviter, quitter, supprimer, annuler, répondre, états lus dans Temporal. `cmd/agent` n'a que des adaptateurs minces : `api` (JSON), `ui` (htmx), `telegramChannel` ; ils changent une session par le service et ne lisent le store que pour afficher (`readStore`)
- Interface de chat (`web/chat` + `cmd/agent/ui.go`) : htmx + `html/template`, trois colonnes (arbre des sessions et forks, fil, rail) et vue carte (`/s/{id}/map`). Rendu côté serveur. Construction des vues pure et testée (`web/chat/views.go`). Fil chronologique (`BuildThread`) : messages hors tour par id, chaque tour en bloc à l'id de son `turn_end`, daté de son début ou « début → fin » (une seule heure dans la même minute), un tour sans fin en bas, « → en cours » (« → interrompu » si son participant a écrit un tour depuis) ; un tour loin de sa question la cite (« ↩ en réponse à … », lien `#m<ancre>`) ; forker un bloc fini part de son `turn_end` (`ThreadItem.ForkID`). Le modèle lit toujours par ancre (`conversation.Order`). Jamais de HTML construit côté client depuis du JSON : le Markdown est rendu côté serveur (`chat.Markdown`, HTML brut échappé)
- Rafraîchissement : le flux SSE n'est qu'une sonnette. Une page a un seul flux (limite de connexions HTTP/1.1), sur `.columns` : `/s/{id}/stream` (topics de la session et de l'arbre du membre), `/tree/stream` sans session. Les événements qui rechargent un panneau sont listés une fois en Go (`session.StateEvents`, `ThreadEvents`, `ReportEvents`, injectés dans `hx-trigger` par `reloadOn`) ; `changed` (topic `tree:<user>`, sonné par `session.Service` quand une session du membre change : tour, question, message et titre, fork, rapport, membre, suppression) recharge l'arbre. Plus de polling régulier : un rechargement par minute en secours. `/sessions/{id}/stream` (API JSON) reste la session seule
- Un flux de session se ferme dès que son utilisateur n'en est plus membre : `relaySSE` vérifie `alive` (`IsMember`) à chaque keep-alive (`sseKeepAlive`, 30 s) et à chaque `member_left` (publié par `Leave` et `Delete`), rejoué ou non. Il finit alors par `session_gone` (`session.EventSessionGone`), envoyé à ce seul abonné, sans id (jamais rejoué) ; `/s/{id}/stream` répond de même, plutôt qu'un 404 qu'EventSource retenterait sans fin, à qui n'est pas membre (vérifié par la route, hors `requireMember`). La page ferme son flux (`sse-close`) et va à `/` (`hx-get`, `hx-push-url`), qui ouvre sa dernière session. Un autre membre parti : la page recharge les avatars et les participants (`#avatars`, `#people`) depuis la page de la session
- Topics du hub : une session = son id (UUID canonique, `session.IsSessionTopic`) ; tout autre topic est `<type>:<id>` (`tree:`, `notifications:`)
- Les panneaux (`#thread`, `#tree`, `#report`, `#agents`) restent en place ; leur contenu est remplacé par morphing (idiomorph 0.8.0, `static/idiomorph-ext-0.8.0.min.js`, `hx-swap="morph:innerHTML"`), le rail et la zone de saisie (hors-bande) aussi. Ids stables ; un morph garde les `<details>` ouverts et le texte saisi (`beforeAttributeUpdated` dans `page.html`), pas de `hx-preserve`. Le fil ne descend en bas que si le membre y était (48 px) ou vient d'envoyer
- Chaque fragment rechargé porte sa version (`data-version`, hash de son rendu, `chat.RenderFragment`), renvoyée dans `X-Fragment-Version` ; inchangé = 204, htmx ne remplace rien. La page porte les versions de ses fragments (`chat.RenderPage`, qui rend chaque fragment une fois et réutilise ces octets) ; marqueur de version tiré au hasard par processus
- Prochain pas de performance : chaque événement de session reconstruit une page entière (`buildPage`) par panneau, onglet et membre (trois sur un fork) ; le 204 n'épargne que le réseau. Un constructeur par fragment (`buildThread`, `buildReport`) est la suite ; le panneau Agents a déjà le sien (`renderAgents`)
- Hub SSE (`sse/`) : chaque événement a un id `<epoch>-<seq>` (epoch = le processus) ; chaque topic garde ses 100 derniers. Les numéros comptent tous les topics : un id place le client dans chacun des topics de son flux. Reconnexion avec `Last-Event-ID` (ou `?last_event_id=`, que la page tient à jour : l'extension htmx recrée l'EventSource sans l'en-tête ; la page part de la position où elle a été rendue, `Hub.Position`) : les événements manqués sont rejoués, sinon (autre epoch, hors du tampon) un seul `reload`. Un abonné trop lent est coupé et rattrape à sa reconnexion
- Tours : le participant envoie `turn_started` (id et nom de l'agent, clé du tour, auteur du message) avant chaque tour et `turn_done` quand il en a fini avec un message (tour persisté et `turn_end` écrit, même en échec ou arrêt ; seul, pour un message sauté : déjà répondu, agent supprimé, vidé par `clear`), sur le web quel que soit le canal. Le serveur les lit au passage dans son hub (`Hub.Observe` → `session.Service.Observe`, en dev comme via `/internal/notify`) : état en mémoire **par participant** (`session/turns.go` : tour en cours, note, messages livrés pas encore commencés), qui prime 30 s sur les requêtes de visibilité (en retard) et invalide le cache des états ; une session travaille tant qu'un de ses participants travaille (le `turn_done` de l'un ne masque pas l'autre). La sonnerie des arbres part en arrière-plan. Oublié après 24 h, ou à la suppression de la session. Événements de tour : une tentative de 3 s (`turnNotifyOptions`), attendue pour l'ordre ; un échec ne bloque rien. Le fil dit « Jarvis travaille… » ou « Jarvis et Smith travaillent… » (`Page.WorkingLine`, avec la note de chacun : `participant` de l'événement `notice`). Sans état (après un redémarrage) : requêtes de visibilité seules, qui nomment les participants en cours
- Panneau « Agents » du rail (`#agents`, fragment `/s/{id}/agents`, rechargé sur `session.AgentsEvents`) : une ligne par participant (`session.Participants` → `chat.BuildAgents`) : l'agent de la session toujours, ceux que les événements ont vus depuis 24 h, ceux que la visibilité voit en cours. Disponible, répond (à qui, depuis quand), attend une réponse (`ask_user` : la visibilité dit quel participant demande), note du tour (attend un worker), messages en file (livrés par ce serveur et pas commencés, comptés tant que le participant tourne ou juste après la livraison ; un relais n'est pas compté), tâches de fond. L'état en mémoire prime ; un participant en cours qu'aucun événement n'a décrit (après un redémarrage) répond à sa requête `state` (en parallèle, 3 s max, gardée 3 s avec les états), seule source des tâches de fond. La ligne « … travaille… » en dérive
- Arrêter (§6 de `docs/design/participants.md`) : « Arrêter » d'une ligne = `stop-turn` à ce participant, permis à l'auteur du message en cours ou au créateur de la session (`session.MayStop`) ; « Tout arrêter » = `clear`, au créateur seul (`MayClear` : il jette les messages des autres), après confirmation. Règles dans `session.Service.StopTurn`/`Clear`/`Cancel` ; pour un autre que le créateur, l'auteur est relu au clic par la requête `state` (jamais le cache), et le signal nomme le tour (`workflow.StopTurn{TurnKey}`, clé portée par le bouton) : le participant ignore un stop pour un autre tour. Clé vide = le tour en cours, quel qu'il soit (créateur seulement). « Arrêter » du fil (`Cancel`) : tous les tours pour le créateur, sinon ceux qui répondent à ses messages ; affiché seulement s'il y en a un. Pas de bouton sans droit. JSON : `POST /sessions/{id}/participants/{agent}/stop` (`{"turn"}` optionnel) et `/clear` ; 403 sans droit, 409 tour fini, 404 rien en cours
- États des sessions lus dans Temporal (3 requêtes de visibilité : `ParticipantWorkflow`, `ForkSessionWorkflow`, `AskUserWorkflow`), partagés 3 s entre toutes les requêtes, invalidés après une action ou un événement de tour, de question, de fork ou de rapport. États : `idle`, `working`, `waiting` (plus d'`active`)
- Comptes (`auth/`) : login email + mot de passe argon2id, cookie `session_token` (token aléatoire, seul son hash est en base dans `login_sessions`). Premier admin : `agent user create --email … --admin`. Échecs de connexion limités en mémoire (`auth.LoginLimits` : 10 par compte sur 15 min, au-delà 429) et journalisés avec l'adresse. La limite par adresse (20) n'existe que si l'adresse du client est connue : `TRUSTED_PROXIES` (CIDR/adresses des reverse proxies, dont on lit `X-Forwarded-For` depuis la droite ; `none` = pas de proxy). Vide (défaut) = pas de limite par adresse : derrière un proxy, tous les clients partagent la sienne et vingt échecs bloqueraient tout le monde. De même pour une requête d'un proxy de confiance qui ne nomme aucun client (`ClientAddrs.Of` = `""`, journalisé une fois). Une route de session vérifie que l'utilisateur en est membre (`requireMember`)
- Worker = Temporal worker + activities + tools publiés sur sa queue (`worker.yaml`)
- Communication worker → serveur via `/internal/notify` ; le reste passe par PostgreSQL (agents, tools, skills_version). `/internal/notify` exige `Authorization: Bearer $INTERNAL_API_KEY` (vide = tout refusé) ; le port interne ne doit pas être publié
- Webhooks : `/webhooks/telegram` vérifie `X-Telegram-Bot-Api-Secret-Token` = `TELEGRAM_WEBHOOK_SECRET`, `/webhooks/skills` la signature GitHub avec `SKILLS_WEBHOOK_SECRET`. Sans secret, la route n'est pas montée (défaut fermé)
- Serveurs HTTP (public, interne, dev) par `newHTTPServer` : `ReadHeaderTimeout` 10 s, `IdleTimeout` 120 s, jamais de `ReadTimeout`/`WriteTimeout` (les flux SSE ne finissent pas) ; un flux SSE inactif envoie un commentaire `: ping` toutes les 30 s (`sseKeepAlive`) pour que les proxies le gardent

## Workflows

- **Pas de workflow de session** : une session n'est que des données. Chaque agent qui y répond est un **participant**, `ParticipantWorkflow` (`<session>:p:<agent>`, `workflow/participant.go`) : il traite sa boîte dans l'ordre, un message à la fois, en parallèle des autres participants, et se termine quand elle est vide. Le serveur livre chaque message par `SignalWithStart` (signal `message`, `ParticipantMessage` : ID du message, auteur, `next`, `earlier_turns`, `sign_reply`, canal, `part` ; **jamais le texte**) ; un signal arrivé pendant la fin est gardé par le serveur Temporal (`UNHANDLED_COMMAND`). Signaux `stop-turn` (le tour seul, `StopTurn{turn_key}` : un stop pour un autre tour est ignoré, clé vide = le tour en cours) et `clear` (le tour et la boîte : chaque message jeté reçoit un `turn_end` « Annulé… ») ; requête `state` (`{current: {message_id, turn, user_id, user_name, since}, queued, background}`). Remise à neuf au-delà de 4000 événements ou 4 Mo, la boîte emportée dans l'entrée
- Autour de chaque tour (`AgentWorkflow` enfant `<participant>:m<id>`), le participant : `CheckTurn` (session encore là, sinon il s'arrête ; `turn_end` déjà écrit = message ignoré, la déduplication en base ; agent lu en base, absent = `turn_end` d'erreur sans tour), `turn_started`, le tour (sélecteur sur la fin, `stop-turn`, `clear` et les nouveaux messages), réécriture idempotente, `EndTurn` (comme `CheckTurn` : 12 essais, environ 2 min de panne de la base tolérées, un worker absent attendu comme le workflow ; seuls agent absent et session supprimée sont définitifs ; échec = journalisé, le tour reste invisible aux autres et serait rejoué), notification d'erreur ou d'interruption, puis relais. Garantie « au moins une fois »
- **AgentWorkflow** : boucle ReAct (LLM + tools), `agent_id` obligatoire (prompt, skills, allowlist). Il ne tient que les messages qu'il produit, jamais l'historique
- **`CallLLM` charge la conversation** (`activity.LLMTurnRequest`) : le workflow ne passe que des références (agent, noms des outils, `PromptRef`, historique par `TurnHistory`) ; une entrée reste de ~160 octets quelle que soit la session, hors `Override` (prompt de remplacement, non plafonné) et `Tail` (après un flush raté). L'activity charge (`LoadConversation`), ordonne (`conversation.Order`), convertit (`conversation.Convert`), reconstruit les définitions d'outils par nom depuis le catalogue (triés par octets dans `SetTools`, pas par la collation de la base ; jamais l'allowlist réappliquée, ce sont les outils que le tour dispatche ; outil disparu en cours de tour : non proposé et journalisé, mais s'il est déjà appelé dans la conversation, gardé en définition minimale « Withdrawn… ne pas l'appeler », hors prompt : l'API refuse des blocs d'outils sans aucun outil défini) et le prompt système à chaque appel (identité, comportements, skills, mémoire de l'utilisateur relue, `PartNote`), puis appelle le fournisseur
- Règle de lecture (`store.TurnReads`, portée `store.ScopeOf(clé, EarlierTurns)`) : un tour lit les messages hors tour jusqu'à son ancre, son tour et ceux d'`EarlierTurns` entiers, les tours de son participant ancrés jusqu'à son ancre (même écrits après), et ceux d'un autre participant entiers ou pas du tout : seulement si leur `turn_end` a un id ≤ ancre. Un `turn_end` n'est jamais lu. `LoadConversation` lit la session en une seule requête (un seul instantané) : il en tire l'ID des `turn_end`, puis filtre en mémoire et ne décode que ce qu'il garde. + `Tail` (ce qu'un flush raté n'a pas écrit, dédoublonné par clé)
- Course connue, non corrigée : ordre des ids ≠ ordre des commits. Un message stocké à quelques ms d'un autre peut prendre un id plus petit et commiter après le début du tour de l'autre : le deuxième appel du tour le lit, placé avant ses messages (préfixe changé, cache manqué). Rarissime, aucune requête invalide pour l'API ; il faudrait un ordre par commit
- Coût : chaque appel relit et reconvertit tout l'historique (non mesuré) ; si ça pèse, cache côté worker du préfixe ordonné par `(session, UpTo, EarlierTurns)`, pas avant
- Mode inline : un sous-agent ou une tâche planifiée (sans `TurnKey`) passe ses propres messages dans `Messages` ; rien n'est chargé ni persisté. Les deux à la fois = refus
- Garde : requête (JSON) > `LLM_MAX_CONTEXT_BYTES` (défaut 2 Mo, `activity.DefaultMaxContextBytes`) = erreur non retentée `ContextTooLong` ; le tour s'arrête avec `activity.ContextTooLongMessage` (« forke-la… ») en `KindTurnError`. Même traduction quand l'API refuse elle-même (« prompt is too long », « input length and `max_tokens` exceed context limit » — celui qu'une conversation qui grandit rencontre d'abord —, 413 : `provider.ErrContextTooLong`, reconnu dans le fournisseur). Le défaut 2 Mo ne protège qu'un modèle à 1M tokens ; en dessous (200K…), c'est le refus de l'API, traduit, qui arrête le tour, sauf à baisser `LLM_MAX_CONTEXT_BYTES`. Requête non sérialisable = garde déclenchée
- **Les sous-agents** : chaque agent est un tool `agent_<id>(task)` généré par le catalogue (pas publié par un worker), soumis à l'allowlist comme les autres (`agent_*` = tous). L'appeler lance un AgentWorkflow one-shot, sans persistance, contexte isolé du parent, avec l'allowlist de son propre agent
- Le parent ne voit que la réponse finale du sous-agent (string) ; sans réponse, un résultat d'outil en erreur qui dit pourquoi (conversation trop longue : « donne-lui une tâche plus petite », jamais le conseil de fork)
- Délégation refusée (erreur d'outil rendue au modèle) vers un agent déjà dans la chaîne d'appel (`AgentChain`, A → B → A) ou au-delà de `maxDelegationDepth` (3) niveaux de sous-agents

## Agents, Tools & Task Queues

- Modèle cible et état : `docs/architecture.md`
- Agent = persona logique identifiée par `agent_id` (prompt, skills, allowlist d'outils). Table `agents` = source de vérité, éditée via `/admin` ; `agents.yaml` = seed, appliqué seulement si la table est vide
- Queue = capacité, jamais un agent ni une machine. Chaque worker lit `worker.yaml` (`WORKER_CONFIG`) : `queue`, `tools` (globs), `mcp`, `workflows`, et publie ses tools dans la table `tools`
- Sans `worker.yaml` : le worker sert workflows + tous les tools sur `WORKFLOW_QUEUE` (défaut `agent`)
- Connexion à Temporal (`dialTemporal`) : en clair par défaut ; TLS avec `TEMPORAL_TLS=true` (CA du système, sans certificat client), `TEMPORAL_TLS_CERT` + `TEMPORAL_TLS_KEY` (mTLS, les deux ou aucun, sinon le processus s'arrête) et/ou `TEMPORAL_TLS_CA` (CA privée) ; `TEMPORAL_TLS=false` avec un certificat ou une CA = arrêt ; `TEMPORAL_TLS_SERVER_NAME` en option, exige TLS (`temporalTLS`)
- Workflows (participants, agents, LLM, forks) sur `WORKFLOW_QUEUE` ; le relais aussi (la queue du participant qui relaie). Chaque appel d'outil part sur la queue de l'outil (`ExecuteTool` générique, queue fixée dans `ActivityOptions`)
- Les workers gardent un catalogue en mémoire (agents + tools) rechargé toutes les 30 s ; `ListTools(agentID)` applique l'allowlist
- Skills chargés depuis un repo Git (prod) ou `./skills` (dev)
- Client MCP (`tool/mcp*.go`) conforme : handshake `initialize` + `notifications/initialized`, version négociée (demande 2025-11-25, accepte jusqu'à 2024-11-05), `api_key` en Bearer. `transport: http` = Streamable HTTP (réponse JSON ou flux SSE, `Mcp-Session-Id` renvoyé, `MCP-Protocol-Version`, 404 = session perdue → nouvelle session et requête renvoyée une fois, flux repris par `Last-Event-ID`) ; `sse` = l'ancien HTTP+SSE (endpoint sur la même origine). Transports dans `mcpTransports` (dialer + indice si le serveur parle l'autre), `worker.yaml` vérifié contre `tool.MCPTransports()`. Redirections jamais suivies (3xx = erreur). Requêtes du serveur : `ping` répondu, le reste refusé (-32601) ; sur l'ancien flux, 4 réponses en vol au plus, les suivantes ignorées. Erreur sans `id` = réponse seulement pour un corps JSON, pas sur un flux
- `tools/list` validé, refusé en entier sinon (le serveur garde ses outils, refus journalisé une fois par changement) : nom exposé = `<serveur>_<outil>` avec `_` à la place de tout caractère hors `[A-Za-z0-9_-]` (l'appel garde le vrai nom), 1 à 64 caractères, deux outils sous un même nom = refus ; 500 outils, description 8 Kio, `inputSchema` objet JSON de 64 Kio, liste entière 4 Mio au plus (lue dans ce budget). Message max : 16 Mio pour `tools/call`, 1 Mio pour `initialize`
- `MCPServers` (`tool/mcp_servers.go`) : au démarrage, découverte en parallèle (10 s max), enregistrement dans l'ordre de la config, filtré par les globs `tools`, puis publication de tout le registre. Ensuite `Run` (contexte du runtime, démarré après cette publication) : un serveur injoignable est réessayé (5 s doublés jusqu'à 5 min), chacun est redécouvert toutes les 30 s, une seule goroutine applique et publie les changements. Un serveur tombé garde ses outils (appels en erreur, liste stable) ; seuls les changements d'état sont journalisés
- Outil retiré par son serveur : désenregistré et supprimé de `tools` par `DeleteTool(nom, queue)`, seulement la ligne de cette queue, jamais un nom qu'une autre source du worker détient. Une publication échouée est retentée à la découverte suivante
- Registre (`tool.Registry`) sous `RWMutex`, chaque outil avec sa source ; un nom pris (outil intégré, serveur précédent) n'est jamais remplacé : l'outil est refusé et journalisé (`SyncSource`)

## Store (PostgreSQL)

- `messages` : historique de conversation par session (JSONB), append-only ; `msg_key` = cle d'idempotence : `msg:{uuid}` (humain), `sched:{id}:{run}` (resultat de tache), `report:…`, `fork-summary:0`, et pour un tour `{tour}:{index}` et `{tour}:end` (sa fin, `store.TurnEndKey`, hors des index qu'une réécriture ignore). Clé de tour `m<id du message>.<participant>` (`store.TurnKey`) : l'ancre après `m` (`TurnAnchor`), le participant après le dernier `.` (`TurnParticipant` : l'agent, `i=<instance>`, `<agent>~btw` plus tard). `TurnOf` ne reconnaît que cette forme. Pas de clé étrangère vers `sessions` ; lecture `ORDER BY id`, puis `conversation.Order` pour le modèle
- `users` (email unique insensible à la casse, rôle `admin`|`user`, `disabled_at`), `login_sessions`
- `sessions` (`created_by`) + `session_members` : une session est partagée entre ses membres ; tout membre peut en ajouter, chacun peut la quitter, seul le créateur la supprime. `Delete` et le `Leave` du dernier membre terminent ses participants (visibilité + événements ; un participant à peine démarré peut survivre, son tour suivant trouve la session absente). `Open` ne démarre rien. `GET /sessions/{id}/state` = liste des états des participants ; `POST /sessions` ne prend que `agent_id` (plus de `system_prompt`/`model`), `/me/sessions` n'a plus `active`
- Chaque message utilisateur porte son auteur (`user_id`, `author`). Un message assistant porte l'utilisateur auquel répond son tour (`user_id`, posé par `AgentWorkflow`), jamais lu comme un auteur (fil, `/api`, résumé de fork, `Order` ne le lisent que sur un message utilisateur). Le serveur enregistre **chaque message humain dès réception** (`session.Service.Deliver`, web et Telegram), qu'il appelle l'agent ou non ; l'agent ne voit que ce que contient l'historique, rechargé en entier à chaque appel LLM
- Qui répond à un message : les agents qu'il mentionne (`@<mention>`), dans l'ordre de première apparition, une fois chacun, au plus `maxAgentsPerMessage` (3, le reste journalisé), quel que soit le mode ; résolus par le serveur (`mentionedAgents`, parmi tous les agents de l'installation : restreindre ceux d'une session viendra plus tard). Sans mention, `sessions.agent_mode` décide si l'agent de la session répond, seul : `auto` (seul dans la session : chaque message ; à plusieurs : jamais sans mention), `always`, `mention`. La mention d'un agent (`agents.mention`, unique sans casse, `[A-Za-z0-9_-]{1,32}`, jamais l'ID d'un autre agent, et un ID jamais la mention d'un autre : `ErrMentionTaken`, vérifié sous verrou consultatif dans la transaction d'écriture, `writeAgent` ; `mentionedAgents` fait passer une mention explicite avant un ID) est choisie par l'admin dans `/admin` ; vide = son ID (`Agent.MentionName`). Une session sans agent prend celle de l'agent par défaut. Le prompt de l'agent dit son nom et sa mention (`identitySection`). `Deliver` dans l'ordre : résout les agents (le texte seul), refuse si le premier a déjà `MaxQueued` (5) messages en attente d'après l'état en mémoire (`ErrQueueFull` : 429, sur Telegram une réponse texte dans la réponse du webhook, rien d'enregistré ; dans le doute on laisse passer, le relais n'est pas compté), enregistre, publie `user_message` (`agents`, `queued_behind` : le message en cours de chaque agent appelé), puis `SignalWithStart` chez le premier. Un tour n'ajoute jamais son message (déjà en base). Le tour répond à son auteur : c'est **sa** mémoire qui est chargée, et ses tools (`save_user_memory`, `schedule_task`) agissent pour lui
- Ordre par ancre (`conversation.Order`) : chaque tour, en bloc, juste après le dernier message hors tour d'id ≤ son ancre ; les tours d'une même ancre (relais) par leur premier id ; les messages hors tour par id. Le tour qui lit finit dernier, jamais sur la réponse d'un autre participant. Identique à l'ancien ordre quand les tours se suivent (test aléatoire `TestOrder_SameAsOneAtATime`). Plus de message humain entre un tool call et son résultat (l'API l'exige)
- Fork : `sessions.parent_session_id` + `forked_at_message_id` + `forked_by`. `POST /sessions/{id}/fork {message_id}` crée la session (même agent, seul membre = celui qui forke) puis `ForkSessionWorkflow` résume le parent jusqu'à ce message (`SummarizeConversation`, modèle `SUMMARY_MODEL` ou `LLM_MODEL`) et l'écrit comme premier message (`kind = fork_summary`) : `PostForkSummary` (`AppendForkSummary`) pose le message et `sessions.summary_message_id` dans une transaction (fork supprimé = `ErrForkGone`, définitif). Tant que `summary_message_id` vaut 0, le fork refuse les messages (409). Supprimer le parent laisse le fork entier, sans lien
- But d'un fork : `purpose` optionnel (formulaire « Pour quoi faire ? » de « Forker ici », pas de `hx-confirm`), rogné, 500 caractères au plus (`session.MaxPurposeRunes`), dans `sessions.fork_purpose`. Donné, il titre le fork et oriente le résumé : la consigne dit de garder ce qui le concerne, cité mot pour mot ; le but lui-même va dans la requête, entre `<goal>` et `</goal>` (`quoteGoal`, balises internes neutralisées), et la consigne dit que c'est le texte cité d'un membre : ni une instruction, ni une partie du transcript (idem pour le rapport)
- Rapport d'un fork : « ⑂ Rapporter au parent » (rail du fork, `POST /s/{id}/report` ; JSON `POST /sessions/{id}/report`, 202), réservé à un membre du fork **et** du parent (sinon la raison, sans bouton : `ErrNotParentMember`, `ErrNoParent`). Le bouton demande confirmation (`hx-confirm` : titre du parent, nombre de ses membres, signé de ton nom) et une `.note` visible dit ce qu'il fait. Refusé/désactivé tant que le brief s'écrit, qu'un rapport s'écrit (la section se recharge toutes les 3 s), ou sans rien de rapportable. Un échec s'affiche 15 min (`reportFailureShown`) ou jusqu'au clic suivant. Règles dans `session.Service.ReportToParent`/`ReportState`
- Rapport partiel : l'agent du fork en plein tour (`working`, ou `waiting` sur un `ask_user`, d'après `Statuses`) ne bloque pas. Le rapport couvre ce qui est écrit, la suite va au rapport suivant. `ReportState.AgentWorking` le dit : bouton actif, confirmation et `.note` « L'agent est en plein tour (il travaille ou attend une réponse) : le rapport couvrira ce qui est écrit jusqu'ici… ». Sur un `ask_user`, la question et sa réponse n'y sont pas (un round n'est écrit qu'avec ses résultats) : elles iront au rapport suivant
- Plage d'un rapport (`reportRange`) : après `last_reported_message_id`, jusqu'au dernier message ; elle s'arrête avant un message assistant du dernier tour dont un tool call n'a pas encore son résultat (`pendingCall`). Garde sur un invariant : un tour écrit un tool call et ses résultats en une seule écriture, donc ce cas n'arrive pas aujourd'hui. « Rapportable » = `activity.Reportable`, même règle que le transcript (`Transcribed`) : une plage sans rien de rapportable ne lance rien
- `ForkSummaryState(ctx, fork)` lit la ligne du fork (`summary_message_id`), et `ForkRunning` (en cache) seulement sans résumé : `Deliver` sur un fork ne charge aucune conversation. `ReportState(ctx, fork, msgs, me)` prend les messages déjà chargés (plage du rapport) : une page de fork, ou la section du rapport, charge sa conversation une fois. Le parent (accès + nombre de membres) : une requête, `SessionMembership`. L'état d'un workflow lu pour une page (`shownWorkflow` : résumé et rapport du fork) est gardé 3 s avec les états des sessions et invalidé avec eux (horloge `statusCache.now`, injectable en test) ; une action qui doit le savoir à l'instant lit `workflowStatus`
- `ReportToParentWorkflow` (ID `report-<fork>-<from>`, `from` = `sessions.last_reported_message_id` : un double clic ne lance rien, seul un échec se relance) : `SummarizeForkReport` résume les messages du fork après `from` (même transcript que le résumé de fork, `PrivateInput` compris ; les appels cherchés dans tous les messages chargés jusqu'à `upTo`, donc un résultat dont l'appel précède `from` garde la règle de son outil ; le brief à part, comme le plan ; but en tête), en quatre parties (fait, décisions, écarts au plan, points ouverts) ; puis `PostForkReport` le poste dans le parent comme message du membre (`Role user`, `kind = fork_report`, `fork` = session, titre, dernier message couvert), clé `report:<fork>:<from>-<upTo>`
- `AppendForkReport` poste le rapport et met à jour le fork (`last_reported_message_id`, `last_report_id`, `last_reported_at`) dans une transaction qui tient la ligne du fork : un retry ne double rien ; fork supprimé (`ErrForkGone`), parent supprimé (`ErrReportParentGone`), rapporteur parti du fork ou du parent, rapport périmé = refus définitifs (`activity.ErrTypeForkGone`, `ErrTypeReport*`, non retentés). Les lignes `session_members` du rapporteur (fork et parent) sont lues `FOR SHARE` : les quitter attend le commit du rapport. `DeleteSession` supprime la ligne avant les messages, pour qu'un rapport en cours ne survive pas au parent
- Un `fork_report` n'appelle aucun agent. L'agent le lit encadré (`[Report from fork « titre » by auteur. …]`), un résumé de fork l'étiquette ; sa clé n'est celle d'aucun tour (`Order`, `TurnReads` : un message de personne). SSE : `fork_report` au parent, `fork_reported` (repère « Rapport envoyé » dans le fil du fork) ou `fork_report_failed` au fork. Un parent de canal `telegram` ne reçoit le rapport qu'en base et en SSE : rien n'est envoyé sur Telegram
- `memory` : key-value scope (user/project/session), avec `version` (+1 à chaque sauvegarde, 0 = jamais sauvée). Toute écriture est conditionnelle : `SaveMemory(…, expected)` n'écrit que si la version est encore `expected` (0 = insertion), sinon `store.ErrMemoryConflict` (sentinelle, sans contenu : on relit par `LoadMemory`) ; pas de chemin last-write-wins. La mémoire d'un utilisateur est partagée par toutes ses sessions et forks
- Version vue par le modèle : `CallLLM` renvoie, avec la réponse, la version de la mémoire mise dans le prompt (`LLMTurnResponse.MemoryVersion`, nil = aucune ; `MemoryUnread` = demandée mais illisible) ; `AgentWorkflow` garde celle du dernier appel et la passe aux outils dans `tool.CallContext` (`MemoryVersion`, `MemoryUnread`). Le modèle ne voit jamais de numéro
- `save_user_memory` (`NeedsCallContext`) sauve depuis cette version. Conflit = résultat en erreur **sans** la mémoire (il reste dans l'historique de la session) : « fusionne dans la version de ton prompt » ; l'appel LLM suivant la relit avec sa version, le nouvel essai passe. Pas de version = refus, jamais d'écrasement à l'aveugle, avec deux messages : mémoire illisible (réessayer à l'étape suivante) ou sous-agent sans mémoire (la mettre dans sa réponse)
- `task_logs` : suivi des taches schedulees, chacune a son `user_id` : `list_schedules` et `cancel_schedule` ne voient que celles de l'utilisateur du tour (aucun outil sans utilisateur identifie). `query_workflow` n'interroge que les workflows de la session appelante (préfixe `<session>:`), requête `state` par défaut
- Plusieurs agents sur un message : le serveur ne livre qu'au premier, avec `next` = les suivants ; son participant, si le tour a réussi (ni échec ni arrêt), relaie par l'activity `Relay` (`SignalWithStart` par le client Temporal ; 5 essais sur 1 min ; un doublon est dédupliqué par `CheckTurn`) avec `next` = le reste et `earlier_turns` cumulés : chacun lit les réponses d'avant. Échec final du relais : `turn_end` d'erreur sous la clé du destinataire (« le relais vers @x a échoué »), notification, le relayeur continue. À plusieurs, chacun reçoit `PartNote` (calculée par le participant depuis `part` : agents dans l'ordre, message cité tronqué, `workflow.Quote`)
- Attribution : un message assistant porte `agent_id` et `author` (nom de l'agent à l'écriture) ; un `KindTurnEnd` porte `agent_id`. Le résumé de fork nomme l'agent. Le fil signe chaque réponse de son agent tel qu'il est (`chat.AgentDirectory`), sinon le nom stocké, sinon l'agent de la session (message sans `agent_id`) ; le rail liste les mentions ; rail et zone de saisie ne parlent des autres agents que s'il y en a plusieurs (`Page.SeveralAgents`). L'événement live `user_message` nomme les agents qui répondent (`agents`, vide = aucun). Sur le canal, une réponse est signée (`SignReply`, champ `agent` de l'événement `message`, Telegram : `Nom :` en tête) quand le message appelait plusieurs agents ou un autre que celui de la session, ses erreurs aussi (`CheckTurn`, tour, relais : signée du relayeur ; de l'ID de l'agent tant que son nom n'est pas lu) ; une question `ask_user` l'est aussi, même règle (`CallContext.Agent`, champ `agent` de l'événement `ask_user`) ; un sous-agent hérite `SignReply` et signe ses questions de son nom
- Ce que lit le modèle (`conversation.Convert`, après `conversation.Order`) : le tour d'un **autre** agent devient du texte, rôle user : `[agent Nom (@mention)] …`, ses appels `[agent … called outil {…}]` (entrée tronquée, masquée si `PrivateInput`), leurs résultats tronqués (masqués aussi si `PrivateInput`). Jamais de blocs tool d'un autre agent : un agent sans outil serait refusé par l'API, et un historique fini sur un message assistant serait continué au lieu de répondu. Un humain : `[Nom] …`. Ses propres messages, et ceux sans `agent_id`, restent des blocs assistant ; mais ses tours pour un **autre** utilisateur (`user_id` non vide et différent de `View.User`) ont l'entrée et le résultat d'un appel `PrivateInput` remplacés par `(private)`, blocs gardés (appariement tool_use/tool_result intact) : en répondant à Bob, l'agent ne relit pas ce qu'il a sauvé pour Alice. Un tour sans `user_id` (antérieur) reste entier, sans rattrapage. Textes user consécutifs fusionnés. Noms et mentions actuels du catalogue (`Catalog.AgentLabels`), outils privés de tout le catalogue (`Catalog.PrivateInput`) ; le prompt explique ces préfixes (`identitySection`)
- AgentWorkflow ecrit ses messages au fil du tour quand `TurnKey` est fourni ; le participant reecrit le meme delta en fin de tour (les memes cles, donc sans effet si deja ecrit). Un sous-agent n'a pas de `TurnKey` et ne persiste rien ; seul un run sans `TurnKey` ajoute son `UserMessage`
- Un tour qui echoue ne doit pas perdre son transcript : `AgentWorkflow` renvoie `Error` dans sa sortie plutot qu'une erreur de workflow (un workflow en echec ne rend aucun resultat). Le participant ecrit toujours la fin du tour (`kind = turn_end`, `store.TurnEnd`), avec l'erreur s'il y en a une, echec dur du workflow compris : le fil ne l'affiche que si elle porte une erreur, le modele, les resumes de fork et l'historique de l'API (sans erreur) ne la voient jamais
- Un tour arrêté (signal `stop-turn`, par participant selon les droits, voir « Arrêter ») : `AgentWorkflow` rend son transcript sans erreur (`cancelledOutput`), le participant attend la fin de l'enfant (la future ne se règle qu'à sa clôture), persiste, écrit le `turn_end`, puis notifie l'interruption ; le relais ne part pas. Un `stop-turn` reçu avant l'annonce d'un tour (`turn_started`), pendant `CheckTurn` compris, est jeté : il ne vise qu'un tour annoncé
- Ne jamais persister un message assistant portant des tool calls sans ses tool results : le tour suivant serait rejete par l'API LLM
- Config via `DATABASE_URL` env var
- Migration automatique au demarrage (CREATE TABLE IF NOT EXISTS)

## Conventions

- Pas de prod pour l'instant : aucun code de compatibilité (repli vers un ancien schéma d'ID, `workflow.GetVersion`, entrée d'un ancien worker). Un changement des commandes d'un workflow casse le rejeu des runs ouverts : on les termine (ou on remet tout à zéro) au déploiement. À la première prod, tout changement de commandes d'un workflow devra être versionné (`GetVersion`) et couvert par un test de replay

- `SystemPrompt` dans les workflow inputs = override manuel ; si vide, prompt construit depuis l'agent (`agent_id`)
- Les tool results remontent comme string au parent. Un workflow-tool renvoie un `tool.Result` (`content`, `is_error`) ou un type qui en porte les champs (`ClaudeCodeOutput.Content`) ; seul un sous-agent (`agent_<id>`) est décodé par type (`AgentWorkflowOutput.Response`)
- Ce qu'est un outil est déclaré avec lui (`tool.Tool`) et publié dans la table `tools` : `Sensitive` (affiché dans `/admin`), `PrivateInput` (entrée **et résultat** cachés aux membres, aux résumés de fork — un résultat dont l'appel manque aussi —, aux autres agents et aux tours du même agent pour un autre utilisateur ; seul le tour de cet utilisateur les lit, `tool.DisplayInput`/`DisplayResult`, ex. `save_user_memory`), `NeedsCallContext` (l'outil reçoit `tool.CallContext` : chaîne d'agents, canal, queue du tour pour notifier, version de mémoire lue ; un workflow-tool dans son entrée, ex. `ask_user`, `analyze_repo`, `implement_feature`, un outil activity dans son contexte via `ExecuteToolInput.Call`, `tool.CallFromContext`, ex. `save_user_memory`), `Timeout` (durée max d'un appel activity/MCP = `StartToCloseTimeout`, lue dans la résolution du catalogue ; 0 ou moins = `tool.DefaultTimeout`, la table refuse un négatif, 120 s ; un outil qui a sa propre limite déclare limite + `TimeoutMargin` pour s'arrêter avant Temporal : `exec` 330 s, MCP 150 s, `grep` et `glob` 90 s, `web_fetch` 60 s). Aucune liste de noms d'outils dans le code
- Tout sous-processus lancé pour un modèle (`exec`, Claude Code) passe par `subproc` : environnement en liste blanche (`subproc.Env`, variables Go : `subproc.GoToolchainNames`), groupe de processus tué au retour de la commande comme à l'annulation (`subproc.KillGroup`), tous les processus de `RUN_AS_UID` tués dès qu'aucune commande du worker ne tourne sous cet uid (`subproc.Runs` : `Hold`/`KillStrays`, aussi avant de reprendre un clone ; une seule par processus worker, partagée par `exec` et Claude Code) — cet uid doit donc être dédié à ce rôle, et exécution sous l'utilisateur `RUN_AS_UID`/`RUN_AS_GID` (`subproc.Identity` : `Apply`, `Env` = son HOME et ses caches Go, jamais ceux du worker). Les deux images créent `agent-run` (uid 10001) et posent `RUN_AS_UID=10001`. Worker root sans `RUN_AS_UID` = `exec` et Claude Code refusés (`subproc.CheckRunAs`). Au démarrage le worker donne à cet utilisateur son HOME et le workspace ; `CLAUDE_CONFIG_DIR` reste au worker : chaque run de la CLI (worker ou `agent claude-code-run`) a sa propre copie (`claudecode.SeedConfigDir` : `.credentials.json`, `.claude.json`, `settings.json`, `CLAUDE.md`, à côté du workspace dans `<dir>.claude`), jetée avec lui ; seul un login OAuth renouvelé revient (`KeepCredentials` : jamais avec `ANTHROPIC_API_KEY`, seulement un JSON qui garde tous les champs du login actuel, journalisé). Sans `CLAUDE_CONFIG_DIR` ni `RUN_AS_UID` (poste de dev), pas de copie : la CLI garde sa configuration par défaut (`claudecode.OwnConfig`). La CLI tourne avec `DISABLE_AUTOUPDATER=1` ; les outils fichiers (`read_file`, `write_file`, `edit_file`, `list_directory`, `grep`, `glob`), qui tournent sous l'utilisateur du worker, n'ouvrent rien par un chemin joint : tout passe par un `os.Root` sur le workspace (`tool/workspace.go`), qui refuse à l'ouverture un lien qui en sort (lien absolu compris), et ils donnent ce qu'ils créent par descripteur (`Identity.GiveFile`) ; `PrepareWorkspace` lui donne le clone, `InspectWorkspace`/`PushBranch` le reprennent (`subproc.Reclaim` du dossier, `subproc.ReclaimTree` de tout `.git` : propriétaire, droits fermés aux autres) avant tout git du worker. Ce n'est toujours pas un bac à sable (lecture de ce que cet utilisateur peut lire)
- Claude Code : modèle (`CLAUDE_CODE_MODEL`, vide = défaut de la CLI) et plafond de dépense par run (`CLAUDE_CODE_MAX_BUDGET_USD`, vide = aucun, invalide = le worker ne démarre pas) fixés par le worker, jamais par le modèle appelant : `max_budget_usd` d'`implement_feature` ne peut que l'abaisser. Une analyse est lancée avec un prompt système qui lui dit qu'elle est en lecture seule et que son rapport est lu par un agent (pas de « je peux corriger »)
- Claude Code : qui paie un run est le choix du worker, `CLAUDE_CODE_AUTH` = `api` (`ANTHROPIC_API_KEY`) ou `subscription` (`CLAUDE_CODE_OAUTH_TOKEN` de `claude setup-token`, sinon le login de la configuration de la CLI) ; vide = le seul identifiant présent, les deux sans mode = le worker ne démarre pas (`claudecode.ResolveAuth`). L'identifiant de l'autre mode n'atteint jamais la CLI (`Auth.Filter`). Un produit livré à une entreprise passe par l'API (ou son plan entreprise), pas par un abonnement personnel
- Claude Code : `repo` (et `ref`/`base`) viennent du modèle. Le worker n'accepte que les dépôts de `CLAUDE_CODE_REPOS` (globs, vide = tout refusé), vérifiés dans `PrepareWorkspace` et `PushBranch` (là où vit la clé), refuse ce qui commence par `-`, et passe `--` / `--end-of-options` à git. Le git du worker ne lit jamais la configuration que le run a pu écrire : `PrepareWorkspace` garde une copie de `.git/config` hors du workspace (`<dir>.gitconfig`) et supprime `.git/hooks` ; `InspectWorkspace` et `PushBranch` la réécrivent toujours, en fichier neuf du worker même inchangée (et retirent `commondir`/`config.worktree`), avant toute commande. Une configuration modifiée par le run = rien n'est poussé. `PushBranch` pousse le commit qu'a listé l'inspection (`<sha>:refs/heads/<branche>`), jamais le ref du clone ; un fichier de `.git` partagé avec un autre chemin (lien dur) = `WorkspaceTampered`, rien n'est poussé. Toute commande git du worker : `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, environnement filtré (`subproc.Env`)
- Un run Claude Code (`analyze_repo`, `implement_feature`) est une session Temporal sur la queue de l'outil (`openRun`, `workflow/claude_code_session.go`) : toutes ses étapes sur le worker qui porte le clone, nettoyage compris (contexte déconnecté dérivé de la session, qui la garde). Worker perdu (session en échec, étape que personne ne prend, étape annulée ou arrêtée par le worker lui-même) = run terminé, rien de poussé, pas de reprise ailleurs, ni nettoyage (il n'attendrait personne : le clone part au redémarrage du worker). `openRun` rend un `run` (contexte, début, durée) : une session qui atteint sa borne (`ExecutionTimeout`) est dite « time limit », pas « worker stopped ». Avant la session, une sonde (`ProbeRunWorker`) sur la queue de l'outil, que tout worker poll même plein : sans réponse en 1 min = « no worker available » ; un worker sans CLI y répond `NoClaudeCLI` (non retenté, échec immédiat) ; elle rend aussi l'attente du worker (`queue_wait_seconds` : `CLAUDE_CODE_QUEUE_WAIT`, défaut 30 min, le workflow ne lit pas l'env d'un worker), qui devient `CreationTimeout`. Seul un worker avec la CLI prend des sessions (`withCodingSessions`). Expirée = « all busy… try again later » (le réglage n'est que dans le log). Après 1 min d'attente, un avis (`EventNotice`) part sur le canal du tour, par la queue du tour (`CallContext.NotifyQueue` : un worker de code n'a pas de notifier) ; Telegram l'affiche (« ⏳ … »), le web sur la ligne « <Nom> travaille… — <avis> » (`session.Observe` : note du tour en mémoire, `WorkingNote` ; `notice` dans `ThreadEvents` seulement, pas un événement d'état). L'attente finie (session ouverte ou non), un second avis à texte vide l'efface, seulement si le premier est parti (`notified`, lu après `stopWaiting()`) ; Telegram ignore un texte vide. Le tour suivant remplace la note. Le choix de la queue est dans `runQueue` seul (future queue de repli)
- Au démarrage, un worker où la CLI est installée supprime les `run-*` (et leurs `.claude`, `.gitconfig`) de `CLAUDE_CODE_WORKSPACE` laissés par un worker mort (`claimRunsRoot` : `RootClaim.Sweep`, `subproc.Reclaim` puis `os.RemoveAll`, jamais à travers un lien). Chaque processus garde un flock partagé sur `<racine>/.workers.lock` (`ClaimRoot`) : seul (verrou exclusif obtenu), il supprime tout puis partage (`Share`) ; sinon, seulement ce qui dépasse `workflow.RunWorkspaceLifetime`
- Échec de la prise du verrou = le worker ne démarre pas : sans verrou, le prochain worker à démarrer se croirait seul et supprimerait ses clones. Un autre processus qui balaie (verrou exclusif) : attente bornée (`rootClaimWait`, 2 min, journalisée), puis échec comme les autres ; l'orchestrateur relance le worker. Jamais de run sans verrou
- Arrêt d'un worker : `shutdown` termine d'abord les runs Claude Code (`activity.RunStop`, champ `ClaudeCodeActivities.Stopper` : pas une méthode du struct, que Temporal enregistrerait comme activité ; seulement où la CLI est installée : CLI tuée, réponse `WorkerStopping`, lue comme worker perdu), puis arrête les workers avec `WorkerStopTimeout` (30 s) pour que la réponse parte avant la sortie. Le SDK arrête le poller de workflows en premier : la réponse est enregistrée par Temporal, mais lue par le prochain worker de la queue (une autre réplique, ou celui-ci relancé). La création de session attend donc ses 30 s pleines : arrêt réel ≈ 30 à 50 s. Docker : `stop_grace_period` 60 s
- `RUN_AS_UID` appartient à un seul processus worker par espace de pids : un processus seul sur sa racine tue au démarrage tout ce qui tourne sous cet uid (`KillStrays`)
- `CLAUDE_CODE_MAX_CONCURRENT_RUNS` (défaut 1) = `MaxConcurrentSessionExecutionSize` du worker de session où la CLI est installée. Au-delà de 1, le worker ne démarre pas (`parseMaxRuns`) : des runs sous le même `RUN_AS_UID` atteignent le clone et les identifiants l'un de l'autre, et un processus égaré survit tant qu'un run tourne (`subproc.Runs` ne tue qu'à zéro). Lever la limite = un uid par slot de run d'abord
- Appel LLM refusé de passage (429, 503, 529…) avec `Retry-After` (secondes ou date HTTP) : le fournisseur rend `provider.RetryAfterError` (sans type Temporal), `CallLLM` le traduit en `NextRetryDelay` ; attente plafonnée à 2 min, valeur absurde (> 1 h, passée, illisible) ignorée = politique de retry
- `web_fetch` ne se connecte qu'à des adresses publiques (vérifiées dans le dialer, après résolution DNS et à chaque redirection), en http(s) uniquement
- `send_email` : les en-têtes viennent du modèle, donc sujet, `reply_to`, `to`, `cc` refusés s'ils contiennent CR ou LF, une adresse par valeur (`net/mail.ParseAddress`), sujet non ASCII encodé (`mime.QEncoding`). Aucune restriction de destinataire hors de l'allowlist de l'agent
- Canaux : un canal = un nom (`web`, `telegram`) porté par la session et les workflows. Sortie : un `activity.Notifier` par canal, enregistré au démarrage du worker dans `NotificationActivities.Notifiers` (`HubNotifier` pour le web, `telegram.Notifier`) ; entrée : un `inboundChannel` (`Name()` + `http.Handler`) monté sur `/webhooks/<nom>`. Ajouter un canal = deux implémentations, sans toucher aux workflows
- Les notifications SSE passent par `/internal/notify` (prod, `activity.HTTPNotifier`, dont l'échec fait échouer l'activity : la politique de retry s'applique ; un worker qui sert les workflows vérifie sa clé au démarrage ; un worker d'outils, `workflows: false`, n'envoie aucune notification et ne la vérifie pas) ou in-memory hub (dev, `HubNotifier`)
- Telegram : une réponse longue part en plusieurs messages, chacun retenté seul ; une fois un message parti, un échec est un `activity.PartialDelivery`, jamais retenté (il renverrait le début) ; un message suivant n'est commencé que s'il reste avant l'échéance de l'activity le temps de le finir, essais compris (sinon `PartialDelivery`) : une activity expirée serait retentée, début compris. `NotifyStep` vers un canal : `channelNotifyTimeout` (1 min)
- Une tâche planifiée tourne pour son utilisateur (`UserID`, `LoadUserMemory` : sa mémoire, sans historique de session)
- ask_user fonctionne pour les sous-agents, web comme Telegram : un sous-agent hérite `Channel`/`ChannelID` de son parent (ses questions vont à l'utilisateur ; sa réponse finale ne part que vers le parent, seul le tour de session — `TurnKey` non vide — répond sur le canal), et une réponse Telegram va à la plus ancienne des `AskUserWorkflow` en cours dont l'ID commence par `<session>:`. Tout workflow d'une session a un ID `<session>:…` : outils d'un tour `<tour>:tool:<outil>:<appel>` (`childWorkflowID`, depuis l'ID du run), session = ce qui précède le premier `:` (`workflow.SessionOf`), participant après `:p:` (`ParticipantOf`). Les requêtes de visibilité n'interpolent que l'UUID de session validé
